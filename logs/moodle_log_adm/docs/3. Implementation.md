# Abstracción e implementación de la solución

Sobre los mecanismos conceptuales descritos se construye una arquitectura orientada a objetos fuertemente tipada en Python. Todo el flujo está orquestado por modelos de **Pydantic v2**, garantizando validación declarativa, tipado estricto, ordenación automática y un encapsulamiento robusto del *pipeline*.

### 1. Capa de normalización y utilidades

* **`Plumber`**: Clase interna de utilidad que expone el método `prepare()` para la limpieza preliminar de registros, como la eliminación de espacios duplicados o caracteres invisibles. Su diseño permite extender fácilmente el diccionario de reglas (`rules`) ante nuevos requerimientos, garantizando que los patrones se precompilan una única vez durante la inicialización del módulo (`compiled_rules`). Esto evita cualquier penalización de rendimiento por compilación de expresiones regulares en tiempo de ejecución durante el procesamiento masivo.

```python
class Plumber:
    # Diccionario interno extensible
    rules = { r"\s+": " " }
    # ... precompilación automática en el arranque ...

Plumber.prepare("The   user\t viewed")
# Resultado: "The user viewed"
```

* **`SortValidator` / `ReverseSortedIterable`**: Validadores personalizados implementados mediante `Annotated` y `AfterValidator`. Fuerzan a que cualquier colección que los implemente (como la lista de `Wrapper` dentro de un *keyword* o las `rules` generales) se ordene automáticamente por longitud descendente al ser instanciada. Esto garantiza algorítmicamente que los delimitadores más específicos tengan prioridad de evaluación, previniendo falsos positivos.

```python
# Ordenación automática al instanciar el modelo:
[["", ""], ["<b>", "</b>"]]
# Resultado interno validado:
[["<b>", "</b>"], ["", ""]]
```

### 2. Capa de dominio y gramática (DSL)

La definición de los tipos de datos se abstrae completamente del código y se inyecta de forma declarativa mediante la configuración YAML, permitiendo que la capa de dominio sea puramente dinámica.

```yaml
# Configuración YAML (Capa de dominio)
keywords:
  int:
    pattern: '-?\d+'
    wrappers: [['"', '"'], ["'", "'"], ['', '']]
    placeholders: ['INTEGER']
  str:
    pattern: '.+?'
    wrappers: [['"', '"'], ["'", "'"]]
    placeholders: ['STRING']
```

* **`Wrapper`**: Objeto `NamedTuple` que encapsula el par `prefix` y `suffix`. Proporciona el método `wraps()` para validar deductivamente si un fragmento literal está contenido entre sus delimitadores, y `wrap()` para envolver la sintaxis final de forma segura aplicando `re.escape`.

```python
wrapper = Wrapper(prefix="'", suffix="'")
wrapper.wraps("'13'") # Resultado: True
wrapper.wrap("(?<userId>-?\\d+)?") # Resultado: "'(?<userId>-?\\d+)?'"
```

* **`Keyword`**: Modelo Pydantic que encapsula la definición de un tipo de dato. Agrupa el patrón base, sus envoltorios admitidos (`wrappers`) y sus comodines (`placeholders`). A través de propiedades calculadas (`@cached_property`), construye dinámicamente `inference_pattern`, generando la disyunción que el motor utilizará para localizar la entidad.

```regex
# Propiedad 'inference_pattern' calculada para la keyword 'int':
'(?:-?\d+|INTEGER)?'|"(?:-?\d+|INTEGER)?"|(?:-?\d+|INTEGER)
```

* **`KeywordDict`**: Contenedor `RootModel` que valida el diccionario global cargado desde el YAML y expone, mediante la propiedad `pattern`, la unión escapada de todas las etiquetas disponibles para la compilación de reglas.

```regex
# Propiedad 'pattern' devuelta:
int|str|any
```

### 3. Capa de compilación de reglas

* **`InferenceGroup`**: Objeto `NamedTuple` que almacena los metadatos transitorios de una etiqueta localizada (nombre, índice de aparición para resolver colisiones, patrón base y lista de envoltorios permitidos) exponiendo un `identifier` único.

```python
InferenceGroup(name="userId", occurrence=0, ...).identifier # Resultado: "userId0"
InferenceGroup(name="userId", occurrence=1, ...).identifier # Resultado: "userId1"
```

* **`InferenceRule`**: Toma la pseudo-expresión del usuario, localiza los *tags* (`{campo:keyword}`) y los traduce mediante un *callback* a patrones nativos de búsqueda de Python (`re.Pattern`), indexando todos los metadatos detectados en un diccionario de objetos `InferenceGroup`.

```regex
# Regla original de usuario:
"user with id {userId:int}"

# Patrón de inferencia compilado (re.Pattern):
"user with id (?P<userId0>'(?:-?\d+|INTEGER)?'|"(?:-?\d+|INTEGER)?"|...)"
```

### 4. Capa de formateo y ensamblado de plantillas

El comportamiento de escape, la resolución de alias y la sintaxis del motor de expresiones regulares de destino se definen en un bloque exclusivo del YAML, dotando al sistema de total agnosticismos respecto a la tecnología subyacente.

```yaml
# Configuración YAML (Capa de formateo)
formatter:
  syntax: '(?<{name}>{pattern})'
  substitutions:
    '[*+?^${}()|\[\]\\]': '\g<0>'
  aliases:
    pageId: [prevPageId, nextPageId]
    userId: [targetUserId]
    courseId: [targetCourseId]
    moduleId: [targetModuleId]
```

* **`Formatter`**: Modelo que administra la sintaxis definitiva y las reglas de escape. Permite configurar declarativamente a través del YAML el motor de destino (generando sintaxis nativa de captura de grupos para Java, PCRE, Python, .NET, etc.). Resuelve los alias configurados a partir del identificador del grupo para la nomenclatura final (ej. `[targetUserId]`) y aplica sustituciones de sanitización (`apply_substitutions`) estructuradas también en la configuración, aislando el texto literal.

```python
# Formateo (sintaxis Java por defecto) y resolución de alias (userId -> targetUserId):
formatter.create_template_group(...) # Resultado: "(?<targetUserId>-?\d+)"

# Sanitización de literales (escape de caracteres reservados de regex como el punto):
formatter.apply_substitutions(".") # Resultado: "\."
```

* **`TemplateBuilder`**: Corazón ejecutor del *pipeline* cuya función `build()` orquesta el proceso en tres fases blindando la estructura formal contra colisiones ("canibalización"):

```text
1. Inferencia (búsqueda de derecha a izquierda y extracción a diccionario temporal):
   "course with id '59'." -> "course with id __TOKEN0__."
   {"__TOKEN0__": "'(?<courseId>-?\d+)?'"}

2. Sanitización (split y escape aislado sobre el texto plano):
   ["course with id ", "__TOKEN0__", "."] -> ["course with id ", "__TOKEN0__", "\."]

3. Ensamblado (restitución del diccionario en los tókenes):
   "course with id '(?<courseId>-?\d+)?'\."
```

#### Análisis de sintaxis de grupos de captura por motor

Dado que la arquitectura se diseñó para exportar plantillas de expresiones regulares compatibles con múltiples lenguajes de programación, la propiedad `syntax` del bloque `formatter` permite adaptar la salida a los distintos estándares de la industria.

A continuación, se resume la sintaxis soportada para la denominación de grupos de captura (*Named Capturing Groups*) según el motor objetivo, todos ellos configurables directamente desde el YAML sin alterar el código de la aplicación:

* **PCRE / .NET**
```regex
(?'name'pattern)
```

* **PCRE / JavaScript / Java / .NET** (Sintaxis adoptada por defecto)
```regex
(?<name>pattern)
```

* **PCRE / Python / Golang / Rust**
```regex
(?P<name>pattern)
```

### 5. Capa de orquestación general

* **`InferenceEngine`**: Fachada principal del motor (`BaseModel`). Facilita la instanciación de la arquitectura completa desde configuraciones declarativas mediante `from_yaml()`. Valida el diccionario de *keywords*, ordena la jerarquía de reglas de inferencia por longitud y actúa como factoría proporcionando objetos `TemplateBuilder` inmutables y listos para el procesamiento masivo a través de su método `get_template_builder()`.

```python
# Punto de entrada principal:
engine = InferenceEngine.from_yaml("config.yaml")
builder = engine.get_template_builder()

# Ejecución masiva:
regex_template = builder.build("The user with id '13' viewed the log...")
```

# Gestión de colecciones y orquestación de carga

La ingesta de datos de entrada y el almacenamiento de los resultados generados por el motor de inferencia se administran mediante una arquitectura de colecciones tipadas (`collections`) y rutinas de inicialización (`loading`). Esta separación garantiza que el motor analítico sea totalmente agnóstico respecto al formato físico de los archivos subyacentes.

### El contenedor estructurado: `LogDict` y su normalización

Para organizar los registros procesados, se define la clase `LogDict`. Internamente, utiliza diccionarios anidados (`defaultdict`) y conjuntos (`set`) para estructurar la información jerárquicamente, garantizando la eliminación automática de registros duplicados:

```text
Component:
    Event:
        - Template / Log
        - Template / Log

```

Además de soportar operaciones algebraicas de fusión (sumas in-place `+=` y estándar `+`) para unificar distintos diccionarios, su método `__str__` aplica una **normalización de salida** al exportar. En lugar de volcar los datos en bruto, aplana la estructura interna y configura rigurosamente el motor YAML (`default_flow_style=False`, `sort_keys=True`, `width=float("inf")`, `allow_unicode=True`) para generar un documento final limpio, estructurado mediante listas con guiones y sin saltos de línea abruptos, priorizando la legibilidad humana.

### Abstracción y flexibilidad en las fuentes de datos (`LogSource`)

El sistema no está atado a formatos de archivo específicos (como CSV rígidos o JSON particulares). Esta flexibilidad se logra mediante la clase base abstracta `LogSource[T]`, que inyecta la lógica de lectura mediante el tipo `TextIOLoader` (una función que recibe un flujo de texto y devuelve una estructura de datos).

Gracias a esto, la fuente de datos desconoce cómo se lee el archivo; simplemente recibe un *loader* nativo (como `json.load`, `yaml.safe_load` o `csv.DictReader`), lee las tuplas universales `(componente, evento, descripción)` y orquesta la extracción clasificando los resultados en diccionarios de éxito (`success_dict`) y fracaso (`failure_dict`).

### Diferencia entre colecciones de registros y árboles de templates

Bajo la abstracción anterior, el sistema diferencia estrictamente dos naturalezas de datos de entrada, cada una con su propia implementación:

* **`RecordFile` (Colección de registros):** Procesan volcados planos u orientados a filas (como un CSV o un JSON exportado directamente de Moodle). Su estructura interna es una lista plana (`RecordCollection`). Dado que los nombres de las columnas pueden variar según el origen, esta clase requiere que se le indique explícitamente una tupla con las claves exactas de extracción (`component`, `eventname`, `description`).
* **`TemplateFile` (Árboles de templates):** Diseñada para archivos que ya contienen un conocimiento estructurado y jerárquico (como recopilaciones de templates anonimizados con *placeholders*). En este caso, la estructura esperada es un `TemplateTree` (diccionarios anidados). Al no ser una lista plana, la clase delega en un `TypeAdapter` con `RootModel` de Pydantic para validar rigurosamente el esquema jerárquico del archivo antes de iterarlo.

### Presets de carga y orquestación masiva

Para simplificar el uso del sistema sin perder la flexibilidad mencionada, el módulo `loading` define **presets** en forma de constantes (`TEMPLATE_FILE_LOADERS`, `RECORD_FILE_LOADERS`, `RECORD_FILE_COLUMNS`). Estos diccionarios mapean automáticamente la extensión de un archivo (`.json`, `.csv`, `.yml`) con su *loader* adecuado y sus columnas por defecto. Por ejemplo, si el sistema detecta un `.csv` de registros, le inyecta automáticamente `csv.DictReader` y busca las columnas capitalizadas `"Component"` y `"Event name"`.

La función de alto nivel `process_sources` actúa como el punto de entrada unificado. Construye el motor de inferencia a partir del YAML, itera dinámicamente sobre todas las rutas proporcionadas (resolviendo el tipo de archivo y el preset correspondiente sobre la marcha) y acumula matemáticamente los resultados:

```python
def process_sources(config_file, record_files, template_files):
    # 1. Configuración del motor y obtención del builder
    builder = InferenceEngine.from_yaml(config_file).get_template_builder()

    master_success_dict = LogDict()
    master_failure_dict = LogDict()

    # 2. Iteración y extracción abstracta instanciando los presets adecuados
    for source in (
        *instance_record_files(record_files),
        *instance_template_files(template_files),
    ):
        success_dict, failure_dict = source.extract_templates(builder)

        # 3. Agregación matemática de los resultados (LogDict += LogDict)
        master_success_dict += success_dict
        master_failure_dict += failure_dict

    return master_success_dict, master_failure_dict

```
