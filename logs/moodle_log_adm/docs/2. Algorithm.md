# Algoritmo para la construcción de plantillas

Para trasladar este modelo conceptual de inferencia a un algoritmo de ejecución en código, se aprovechan las capacidades de inspección de texto y metadatos posicionales que proporciona el módulo nativo de expresiones regulares de Python (`re`).

Para ilustrar este flujo de forma concreta, considérese el procesamiento de la siguiente línea de log de ejemplo:

```text
The user with id '13' viewed the log report for the course with id '59'.
```

---

### 1. Indexación de grupos y extracción de metadatos del *Match*

Los motores de expresiones regulares en general (Python, Java, PCRE, etc.) prohíben la presencia de múltiples grupos de captura nombrados que compartan el mismo identificador dentro de un único patrón.

Dado que en los registros de Moodle una misma entidad (como un ID de usuario o un ID de curso) puede aparecer en repetidas ocasiones dentro de una sola frase o regla de inferencia, surge la necesidad técnica de resolver esta colisión sintáctica. Para superar esta restricción, la arquitectura de compilación **indiza sistemáticamente los nombres de los grupos** agregando un sufijo numérico incremental unívoco a cada etiqueta identificada:

```text
Entrada usuario:  "... user {userId:int} ... affected user {userId:int} ..."
Grupo compilado:  (?P<userId0>...) y (?P<userId1>...)
```

Esta indización explícita cumple dos funciones críticas dentro del sistema:

1. **Evitar excepciones sintácticas en el motor regex:** Garantiza que el patrón resultante sea interpretable de forma nativa por cualquier motor sin violar la unicidad de nombres de grupos.
2. **Facilitar la resolución de alias:** Otorga a la capa de formateo una clave unívoca interna para determinar el nombre definitivo de la variable, permitiendo mapear la primera ocurrencia (`userId0`) al nombre base `userId` y las ocurrencias secundarias (`userId1`) a alias configurados explícitamente (ej. `affectedUserId`).

De este modo, las pseudo-expresiones escritas por el usuario se traducen internamente a reglas de inferencia compiladas con sintaxis nativa de Python (`re`) e identificadores indizados:

```regex
user with (?:the )?id (?P<userId0>'(?:-?\d+|INTEGER)?'|"(?:-?\d+|INTEGER)?"|<b>(?:-?\d+|INTEGER)?<\/b>|(?:-?\d+|INTEGER))
course with id (?P<courseId0>'(?:-?\d+|INTEGER)?'|"(?:-?\d+|INTEGER)?"|<b>(?:-?\d+|INTEGER)?<\/b>|(?:-?\d+|INTEGER))
```

Al ejecutar estas reglas compiladas sobre la línea de log de ejemplo, la coincidencia genera una instancia de `re.Match`. Mediante la inspección de este objeto se extrae la información espacial y descriptiva de cada grupo capturado:

```python
>>> match.groupdict()
{'userId0': "'13'", 'courseId0': "'59'"}

>>> match.span('userId0')
(17, 21)

>>> match.span('courseId0')
(67, 71)
```

A partir de esta inspección se obtiene la información fundamental para la transformación:

* **Identificador indizado:** La clave devuelta por el motor (ej. `userId0`), que vincula la captura con sus metadatos de origen evitando colisiones.
* **Valor literal:** La cadena exacta capturada en el registro, reteniendo los delimitadores originales (ej. `"'13'"` para el usuario y `"'59'"` para el curso).
* **`start` / `end`:** Índices de posición absolutos (*offsets*) en el texto procesado devueltos por `span()` (ej. posiciones 17 a 21 para `'13'`).

---

### 2. Deducción del envoltorio real

Una vez identificadas las posiciones de los valores en el texto, el sistema debe deducir cómo estaba delimitado cada valor para poder estructurar su expresión regular definitiva.

Tal y como se define en la configuración YAML anterior, un valor numérico puede presentarse envuelto de múltiples formas (incluyendo el envoltorio vacío `["", ""]` para valores en crudo sin delimitadores). El algoritmo evalúa la cadena literal capturada (`"'13'"`) iterando secuencialmente sobre cada par `[prefijo, sufijo]` definido en la lista de *wrappers*. Para garantizar precisión algorítmica, esta evaluación se ejecuta estrictamente **de mayor a menor longitud total del envoltorio** (sumando los caracteres del prefijo y del sufijo).

Esta ordenación descendente es crítica para evitar falsos positivos. Si el envoltorio vacío se evaluara en primer lugar, las condiciones de validación (`startswith("")` y `endswith("")`) devolverían verdadero de forma inmediata. El motor deduciría erróneamente que el valor capturado `"'13'"` carece de delimitadores, generando un patrón restrictivo y dejando las comillas originales incrustadas como texto literal huérfano. Forzando esta prioridad por longitud, los delimitadores más específicos se evalúan primero:

```text
Evaluación secuencial (por longitud) para el valor capturado "'13'":
1. ¿Empieza por "<b>" y termina en "</b>"? -> Falso (Longitud 7)
2. ¿Empieza por '"' y termina en '"'?    -> Falso (Longitud 2)
3. ¿Empieza por "'" y termina en "'"?    -> ¡Verdadero! (Envoltorio detectado)
```

Una vez localizado el envoltorio activo (`["'", "'"]`), el sistema determina la sintaxis definitiva evaluando la longitud de dichos delimitadores:

* **Con delimitadores (ej. comillas `'`):** El patrón de contenido se declara opcional `?` para tolerar valores vacíos emitidos por el log (`''`). *Resultado:* `'(?<userId>-?\d+)?'`
* **Sin delimitadores (envoltorio vacío `["", ""]`):** El valor se exige obligatoriamente para evitar coincidencias nulas no deseadas en espacios libres. *Resultado:* `(?<userId>-?\d+)`

---

### 3. Inyección de tókenes mediante procesamiento inverso de *offsets*

Una vez deducido el envoltorio y generado el patrón definitivo para cada campo, el objetivo es sustituir el valor literal en el texto original por un token opaco (`__TOKEN1__`) y guardar su expresión regular en un diccionario privado en memoria:

```python
{
    "__TOKEN1__": "'(?<userId>-?\\d+)?'",
    "__TOKEN0__": "'(?<courseId>-?\\d+)?'"
}
```

Sin embargo, llevar a cabo esta sustitución de valores por tókenes directamente sobre el texto plantea un problema posicional inmediato: si las sustituciones de texto se hicieran de izquierda a derecha, la modificación del primer grupo alteraría la longitud global de la cadena y corrompería de forma inmediata los índices de posición (*offsets*) de todas las capturas posteriores.

Por ejemplo, al reemplazar el valor `'13'` (longitud de 4 caracteres) por el marcador `__TOKEN1__` (longitud de 9 caracteres), la cadena se expande en 5 posiciones hacia la derecha. Como consecuencia, la posición de inicio del grupo `courseId0`, calculada previamente por el motor regex en el índice 67, se desplazaría erróneamente a la posición 72. Intentar reemplazar el segundo grupo utilizando su tupla de metadatos original `(67, 71)` provocaría un recorte desalineado sobre el texto literal, corrompiendo la integridad de la plantilla.

Para resolver este desplazamiento espacial de forma matemáticamente limpia y sin necesidad de reevaluar la expresión regular, las capturas extraídas se ordenan y procesan rigurosamente en **orden inverso a su posición de inicio** (`reverse=True` sobre la propiedad `start`):

```text
Cadena original:
"The user with id '13' viewed the log report for the course with id '59'."

1. Primer reemplazo (grupo situado más a la derecha: 'courseId0' en pos. 67-71):
"The user with id '13' viewed the log report for the course with id __TOKEN0__."

2. Segundo reemplazo (grupo situado a la izquierda: 'userId0' en pos. 17-21):
"The user with id __TOKEN1__ viewed the log report for the course with id __TOKEN0__."
```

Al modificar siempre en primer lugar el extremo derecho del texto, los índices de las zonas aún no procesadas situadas a la izquierda permanecen inalterados y matemáticamente válidos, garantizando que cada inyección de token se efectúe exactamente en su posición original.

---

### 4. Sanitización aislada y prevención de interferencias

Tras aplicar los reemplazos inversos, el registro se encuentra en un estado intermedio donde el texto literal se intercala con los marcadores opacos:

```text
The user with id __TOKEN1__ viewed the log report for the course with id __TOKEN0__.
```

Es necesario someter el texto literal remanente a una fase final de limpieza (por ejemplo, escapar caracteres reservados de expresiones regulares como puntos `.` o paréntesis `()`). Si los bloques de captura generados ya hubieran sido inyectados directamente en la cadena, un proceso global de sanitización alteraría su propia sintaxis automatizada (escapando paréntesis y cuantificadores) y produciría expresiones inválidas. Este tipo de interferencia destructiva, donde una transformación de limpieza altera la estructura de código que la rodea, puede describirse de forma intuitiva como una **«canibalización» sintáctica**.

Para evitar que el proceso de limpieza destruya las expresiones regulares, los **tókenes temporales** actúan como barreras de aislamiento mediante un ensamblado en cuatro pasos:

1. **Fragmentación segura:** La cadena se divide utilizando los propios tókenes como puntos de corte (mediante `re.split(r"(__TOKEN\d+__)")`).
2. **Sanitización dirigida:** Se iteran los fragmentos resultantes y únicamente los textos literales (ej. `" viewed the log report for the course with id "`) reciben las reglas de limpieza y escape, sin riesgo para el motor formal.
3. **Restitución:** Si el fragmento es un token (`__TOKEN1__`), se recupera de manera transparente su expresión regular intacta desde el diccionario privado en memoria.
4. **Unión unificada:** Se ensamblan todos los fragmentos procesados en una única pasada, devolviendo la plantilla unificada, exacta y validada:

```regex
The user with id '(?<userId>-?\d+)?' viewed the log report for the course with id '(?<courseId>-?\d+)?'\.
```
