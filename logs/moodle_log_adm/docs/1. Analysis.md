# Análisis del enfoque "Template matching"

Teniendo en cuenta la existencia de registros crudos (*raw logs*) con alta variabilidad estructural, considérense los siguientes ejemplos de origen:
```text
Evento: Logs > Log report viewed
Descripción: The user with id '13' viewed the log report for the course with id '59'.

Evento: H5P > xAPI statement received
Descripción: The user with the id '49' send a tracking statement for a H5P activity with the course module id '1179'.
```

Como se puede observar, componentes distintos utilizan patrones diferentes. Para detectar estas variaciones se pueden emplear expresiones regulares directas:
```regex
The user with id '(\d+)' viewed the log report for the course with id '(\d+)'.
The user with the id '(\d+)' send a tracking statement for a H5P activity with the course module id '(\d+)'.
```

La extracción sistemática mediante este enfoque plantea diversos problemas a resolver:

* **Identificación semántica:** Los grupos de captura anónimos (`$1`, `$2`) no aportan contexto sobre qué entidad se está extrayendo (un ID de usuario, de curso, etc.).
* **Valores vacíos:** El patrón debe soportar la ausencia total de un valor sin romper la coincidencia global de la cadena.
* **Identificadores numéricos especiales:** [Los procesos automáticos del sistema, *cron* o comandos CLI de Moodle utilizan el identificador `-1`](https://github.com/moodle/moodle/blob/46c042e7da65f8cb2ec7dc19f46566ce61a393e1/public/lib/classes/event/base.php#L94), requiriendo la captura de enteros negativos.
* **Variabilidad en delimitadores:** Diferentes componentes pueden envolver los valores entre comillas simples (`'`), comillas dobles (`"`) o delimitadores asimétricos y multicarácter (`()`, `[]`, `<b>...</b>`). Conviene aclarar que, aunque Moodle no emplea etiquetas HTML en sus registros, estas se incluyen en la modelización para ejemplificar el soporte de envoltorios que no son necesariamente simétricos ni poseen la misma longitud en su prefijo y sufijo.

Estas casuísticas se pueden resolver estructurando expresiones regulares más complejas que combinen grupos de captura con nombre, cuantificadores de opcionalidad y alternativas para los distintos envoltorios:

```regex
The user with id (?<userId>'(?:-?\d+)?'|"(?:-?\d+)?"|<b>(?:-?\d+)?<\/b>) viewed the log report for the course with id (?<courseId>'(?:-?\d+)?'|"(?:-?\d+)?"|<b>(?:-?\d+)?<\/b>).

The user with the id (?<userId>'(?:-?\d+)?'|"(?:-?\d+)?"|<b>(?:-?\d+)?<\/b>) send a tracking statement for a H5P activity with the course module id (?<moduleId>'(?:-?\d+)?'|"(?:-?\d+)?"|<b>(?:-?\d+)?<\/b>).
```

Como se puede observar, intentar resolver manualmente estas casuísticas genera expresiones extremadamente voluminosas, redundantes y proclives a errores de sintaxis. Esta complejidad convierte el mantenimiento manual de un catálogo de más de 200 o 300 expresiones regulares en una tarea completamente inviable, ya que el desarrollador no solo debe gestionar la lógica de captura, sino también escapar minuciosamente caracteres literales conflictivos como `.()[]{}`. Por todo ello, resulta imprescindible introducir una capa de abstracción basada en inferencia.

### Inferencia y desacoplamiento (DSL)

Para inferir automáticamente la presencia de una entidad sin necesidad de construir una expresión regular rígida que abarque toda la línea del log, el problema se aborda mediante **reglas de inferencia** basadas en anclas locales o sub-expresiones descriptivas. Si una regla de inferencia localiza una coincidencia en un fragmento del registro, se determina con seguridad la presencia y posición de la entidad:

```text
Texto crudo:
The user with id '13' viewed the log report for the course with id '59'.

Reglas de inferencia (basadas en anclas locales):
1. user with (?:the )?id '(?<userId>-?\d+)?'
2. course with id '(?<courseId>-?\d+)?'
```

Sin embargo, aunque acotar la búsqueda a anclas locales reduce drásticamente la superficie de texto a analizar, la detección del campo individual sigue sufriendo exactamente los mismos problemas estructurales analizados en el apartado anterior (variabilidad de delimitadores, valores opcionales, números negativos, etc.). A medida que se añaden nuevos envoltorios o casuísticas a soportar, escribir y mantener manualmente estos patrones internos en cada regla de inferencia sigue resultando inmanejable.

Para resolver esta complejidad, es necesario abstraer al desarrollador de la sintaxis directa de expresiones regulares mediante **pseudo-expresiones regulares**. Este Lenguaje Específico de Dominio (DSL) debe permitir definir reglas de inferencia declarando la presencia de campos mediante etiquetas asociadas a tipos de dato (*keyword*):

```regex
user with (?:the )?id {userId:int}
course with id {courseId:int}
```

La etiqueta `int` se mapea contra una especificación declarativa en YAML que define las reglas de análisis del tipo:

```yaml
keywords:
  int:
    pattern: '-?\d+'
    wrappers: [["'", "'"], ['"', '"'], ["<b>", "</b>"], ["", ""]]
    placeholders: ['INTEGER']
```

Aclaraciones sobre la estructura de metadatos:

* **Pattern:** Regla base de coincidencia para el tipo de dato subyacente (ej. enteros que contemplan el signo negativo `-?\d+`).
* **Wrappers:** Definición explícita e independiente de prefijos y sufijos para delegar la detección de delimitadores asimétricos o multicarácter. Conviene aclarar que, aunque Moodle no emplea etiquetas HTML en sus registros, el uso de `<b>...</b>` se incluye en la modelización exclusivamente para ilustrar la potencia y flexibilidad que puede llegar a ofrecer el tratamiento de envoltorios de forma desacoplada. Adicionalmente, se incluye explícitamente el envoltorio vacío (`["", ""]`) para soportar valores en crudo que no posean delimitadores.
* **Placeholders:** La necesidad de reutilizar o analizar bases de datos de plantillas preexistentes (como el [catálogo del repositorio de *UBUMonitor Desktop*](https://github.com/yjx0003/UBUMonitor/blob/master/python/Componentes%20y%20eventos.json)) introduce la exigencia de reconocer marcadores de tipo explícitos en lugar de valores numéricos reales. El patrón base y los *placeholders* (ej. `INTEGER`) se combinan internamente mediante disyunciones (`|`).

Finalmente, un compilador dedicado traduce las pseudo-expresiones regulares, expande las etiquetas según la configuración YAML y sitúa el grupo de captura con nombre en la posición más exterior, englobando de forma unificada todas las combinaciones de envoltorios y marcadores:

```regex
user with (?:the )?id (?<userId>'(?:-?\d+|INTEGER)?'|"(?:-?\d+|INTEGER)?"|<b>(?:-?\d+|INTEGER)?<\/b>|(?:-?\d+|INTEGER))
course with id (?<courseId>'(?:-?\d+|INTEGER)?'|"(?:-?\d+|INTEGER)?"|<b>(?:-?\d+|INTEGER)?<\/b>|(?:-?\d+|INTEGER))
```
